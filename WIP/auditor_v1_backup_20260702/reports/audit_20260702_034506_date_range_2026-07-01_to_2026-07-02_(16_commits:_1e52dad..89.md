## 🚨 Tier: LOGIC

**Go-Live Safe**: NO

### Summary

The ChronomancerCache→DailyForecast rename is structurally complete in src2/ but leaves critical gaps: (1) src/services/compliance.py GDPR delete path still references the old ChronomancerCache model and chronomancer_cache table — this is a silent failure path that will NOT delete daily_forecasts rows during GDPR erasure. (2) The src2/ db.py save_daily_forecast uses the old column name 'narrative_cache' in its constructor kwarg instead of the renamed 'narrative' column, creating a mismatch between the ORM model and the migration. (3) admin/clear_daily_forecasts.py and admin/reset_90.py reference a non-existent db.SessionLocal() attribute, causing runtime AttributeError on --all path. (4) The src2/core/schemas/__init__.py does not export DailyForecastRecord, making the schema undiscoverable. (5) git_push_agent.py contains a hardcoded absolute workspace path and hardcoded branch name. (6) The legacy src/ codebase (src/bot/db.py, src/bot/chronomancer_handler.py, src/database/models.py, src/services/compliance.py, scripts/migrate_sqlite_to_pg_all.py, TEST/unit/day1/test_day1_schema.py) still references ChronomancerCache — these are legacy files but the compliance.py one is actively dangerous.

### Risk Ledger

#### 1. 🔴 [Critical] `src/services/compliance.py:forget_user() lines 123-124`

**Description**: GDPR forget_user() deletes from ChronomancerCache (the old src/database/models.py model pointing to 'chronomancer_cache' table). The Alembic migration renamed the table to 'daily_forecasts'. This delete will either hit a stale/empty table or fail silently depending on whether the old table still exists. User daily forecast data WILL NOT be deleted during GDPR erasure — a compliance violation.

**Mitigation**: Update src/services/compliance.py to import DailyForecast from src2.core.database.models and delete from DailyForecast instead of ChronomancerCache. Alternatively, if this legacy compliance module is still the active GDPR path, it must be fully migrated to use the src2/ model.

#### 2. 🔴 [Critical] `src2/interfaces/telegram/db.py:save_daily_forecast() line 850`

**Description**: The DailyForecast ORM model (src2/core/database/models.py line 115) defines the column as 'narrative' (renamed from 'narrative_cache' by migration 2e4757268cbd). However, save_daily_forecast() constructs new DailyForecast objects with 'narrative_cache=narrative_cache' (line 850), referencing the OLD column name. SQLAlchemy will raise an AttributeError/TypeError because the model has no 'narrative_cache' attribute — only 'narrative'. This breaks ALL new daily forecast inserts.

**Mitigation**: Change line 850 from 'narrative_cache=narrative_cache' to 'narrative=narrative_cache'. Also update line 840 'c.narrative_cache = narrative_cache' to 'c.narrative = narrative_cache'. Update get_daily_forecast() and get_daily_forecast_range() return dicts to read 'c.narrative' instead of 'c.narrative_cache'.

#### 3. 🔴 [Critical] `admin/clear_daily_forecasts.py line 65 and admin/reset_90.py line 51`

**Description**: Both scripts call 'async with db.SessionLocal() as session:' but the Database class in src2/interfaces/telegram/db.py has NO 'SessionLocal' attribute. It has 'Session' (sync scoped_session) and module-level '_async_session_factory'. This will raise AttributeError at runtime, making the --all clear path completely non-functional.

**Mitigation**: Replace 'db.SessionLocal()' with the correct async session accessor. The module-level '_async_session_factory' is the async sessionmaker. Use 'async with _async_session_factory() as session:' or expose a proper async context manager on the Database class.

#### 4. 🟠 [High] `src2/core/schemas/__init__.py`

**Description**: The __init__.py for schemas is empty (just a docstring). DailyForecastRecord is defined in daily_forecast.py but never exported from the package __init__.py. Any code doing 'from src2.core.schemas import DailyForecastRecord' will fail with ImportError. Currently forecast_store.py imports directly from the submodule, but this is fragile and non-standard.

**Mitigation**: Add 'from .daily_forecast import DailyForecastRecord' to src2/core/schemas/__init__.py.

#### 5. 🟠 [High] `src2/interfaces/telegram/db.py:save_daily_forecast() lines 832-833`

**Description**: When an existing record has is_permanent=True, save_daily_forecast() silently returns without updating anything. This is a silent data loss path: callers (forecast_store.py get_daily_forecast, coordinator.py handle_daily) expect their save to persist, but it silently does nothing. No log warning, no error raised. The caller's narrative/score data is discarded.

**Mitigation**: At minimum, log a warning when skipping a permanent record. Better: raise a specific exception or return a sentinel value so callers can detect the skip. The current silent return violates KI 05 Hard Rule 1 (No Silent Failures).

#### 6. 🟠 [High] `src2/interfaces/telegram/chronomancer/coordinator.py:handle_daily() lines 284-293`

**Description**: handle_daily() calls db.save_daily_forecast() with keyword 'narrative=response' but the method signature has 'narrative_cache' as the parameter name. This is a keyword argument mismatch — Python will raise TypeError: save_daily_forecast() got an unexpected keyword argument 'narrative'.

**Mitigation**: Change line 284-293 to use 'narrative_cache=response' to match the current method signature, or rename the parameter in save_daily_forecast() to 'narrative'.

#### 7. 🟠 [High] `src2/interfaces/telegram/chronomancer/forecast_store.py:get_daily_forecast() lines 52-53`

**Description**: get_daily_forecast() calls db.get_daily_forecast() which returns a dict, then accesses 'cached.profile_hash' as if it were a DailyForecastRecord object. Dicts don't have attribute access — this will raise AttributeError. The function signature says it returns DailyForecastRecord | None but the cache-hit path returns a raw dict.

**Mitigation**: Either (a) change db.get_daily_forecast() to return a DailyForecastRecord using from_attributes, or (b) change the cache-hit check to use dict access: 'cached.get("profile_hash") == profile_hash' and then construct a DailyForecastRecord from the dict.

#### 8. 🟠 [High] `src2/interfaces/telegram/chronomancer/forecast_store.py:get_rolling_30() lines 94-95`

**Description**: Same dict-vs-object mismatch: 'cached_records = db.get_daily_forecast_range(...)' returns list[dict], but line 95 does 'cached_by_date = {r.date.isoformat(): r for r in cached_records}' — dicts have no .date attribute. Also line 99 checks 'c.profile_hash' on a dict. This will raise AttributeError on every get_rolling_30 call with cache hits.

**Mitigation**: Use dict access: 'r["date"]' and 'c.get("profile_hash")'. Or refactor db methods to return DailyForecastRecord objects via from_attributes.

#### 9. 🟡 [Medium] `admin/git_push_agent.py line 10`

**Description**: WORKSPACE_ROOT is hardcoded to '/home/yapilwsl/arthityap/baziforecaster'. This breaks portability — the script will fail on any other machine or if the user's home directory changes. Also line 8 of the agent instructions hardcodes 'git push origin rollout-pydantic' — the branch name is baked into the agent prompt.

**Mitigation**: Replace hardcoded path with Path(__file__).resolve().parents[1] or similar relative resolution. Make the push branch configurable via environment variable or CONTROL_SHEET.

#### 10. 🟡 [Medium] `src2/interfaces/telegram/db.py:delete_all_user_data() line 978`

**Description**: delete_all_user_data() filters DailyForecast deletion with 'not DailyForecast.is_permanent', meaning permanent records survive GDPR deletion. This may be intentional but is undocumented and inconsistent with the legacy src/bot/db.py delete_all_user_data which deletes ALL ChronomancerCache rows unconditionally. If permanent records should survive, this needs explicit documentation.

**Mitigation**: Document the is_permanent retention policy explicitly. If GDPR requires full erasure, remove the is_permanent filter for the delete_all_user_data path.

#### 11. 🟡 [Medium] `src2/interfaces/telegram/db.py:save_daily_forecast() parameter name`

**Description**: The parameter is named 'narrative_cache' (line 821) but the ORM model column is 'narrative'. This naming mismatch persists throughout the method: the local variable and kwarg use the old name. While the migration renamed the DB column, the code still carries the obsolete name, creating confusion and potential for future bugs.

**Mitigation**: Rename the parameter from 'narrative_cache' to 'narrative' throughout save_daily_forecast, get_daily_forecast, and get_daily_forecast_range.

#### 12. 🟢 [Low] `src2/core/schemas/daily_forecast.py:DailyForecastRecord`

#### 13. 🟢 [Low] `TEST/unit/day1/test_day1_schema.py`

#### 14. ℹ️ [Informational] `scripts/migrate_sqlite_to_pg_all.py`
