## 🚨 Tier: TELEMETRY

**Go-Live Safe**: NO

### Summary

The ChronomancerCache→DailyForecast rename is complete in src2/ with zero stale references. However, a Critical column-name mismatch exists: the SQLAlchemy model defines `narrative` but db.py reads/writes `narrative_cache` — this will cause silent AttributeError failures on all narrative read paths. Additionally, coordinator.py line 247 uses dict-style access `scored['narrative']` on a Pydantic model, which will raise a TypeError at runtime. The git_push_agent has a hardcoded workspace path and the admin/dotenv.py leaks an API key in plaintext. Multiple TODO markers remain in engine code.

### Risk Ledger

#### 1. 🔴 [Critical] `src2/interfaces/telegram/db.py lines 840, 850, 877, 908 — `narrative_cache` attribute vs model column `narrative``

**Description**: The SQLAlchemy model `DailyForecast` (models.py line 115) defines the column as `narrative = Column(Text)`. However, db.py's `save_daily_forecast` writes to `c.narrative_cache` (line 840) and constructs new records with `narrative_cache=narrative_cache` (line 850). `get_daily_forecast` reads `c.narrative_cache` (line 877). `get_daily_forecast_range` reads `c.narrative_cache` (line 908). Since the model has no `narrative_cache` attribute, these will raise `AttributeError: 'DailyForecast' object has no attribute 'narrative_cache'` at runtime. This is a silent failure path — the `save_daily_forecast` call in coordinator.py line 284 passes `narrative=response` which maps to the parameter name `narrative_cache` in the function signature, but the function body writes to the non-existent model attribute. The Alembic migration (2e4757268cbd) renamed the column from `narrative_cache` to `narrative`, but db.py was never updated to match.

**Mitigation**: In db.py: rename all `narrative_cache` references to `narrative` — lines 821 (parameter name), 839-840 (update path), 850 (insert path), 877 (get_daily_forecast return dict), 908 (get_daily_forecast_range return dict). Also rename the function parameter `narrative_cache` to `narrative` in `save_daily_forecast` signature (line 821) and update all callers (coordinator.py line 284 already passes `narrative=response` which matches).

#### 2. 🔴 [Critical] `src2/interfaces/telegram/chronomancer/coordinator.py line 247 — dict access on Pydantic model`

**Description**: Line 247: `scored['narrative'].strip()` uses dict-style bracket access on `scored`, which is a `DailyForecastRecord` Pydantic model (returned by `get_daily_forecast`). Pydantic v2 models do not support `__getitem__` by default. This will raise `TypeError: 'DailyForecastRecord' object is not subscriptable`. The same variable is correctly accessed as `scored.narrative` on lines 239 and 243, proving the inconsistency.

**Mitigation**: Change line 247 from `scored['narrative'].strip()` to `scored.narrative.strip()` to match the attribute-access pattern used on lines 239 and 243.

#### 3. 🟠 [High] `src2/interfaces/telegram/chronomancer/coordinator.py line 30 — `Database("bot.db")` hardcoded SQLite path`

**Description**: coordinator.py line 30 instantiates `db = Database("bot.db")` at module level. The Database constructor (db.py line 152-154) resolves `"bot.db"` to `os.getenv("BOT_DB_PATH") or "bot.db"`, which means it falls back to a local SQLite file. In PostgreSQL production, this module-level instantiation may connect to the wrong database backend before the environment is fully configured. The forecast_store.py module (line 10) correctly uses `Database()` (no argument), which triggers the PostgreSQL path. This inconsistency means coordinator.py's `db` object may be SQLite while forecast_store.py's `db` is PostgreSQL.

**Mitigation**: Change coordinator.py line 30 from `db = Database("bot.db")` to `db = Database()` to match forecast_store.py and let the constructor auto-detect PostgreSQL vs SQLite based on DATABASE_URL env var.

#### 4. 🟠 [High] `admin/git_push_agent.py line 11 — hardcoded absolute workspace path`

**Description**: `WORKSPACE_ROOT = Path("/home/yapilwsl/arthityap/baziforecaster").resolve()` is a hardcoded absolute path to a developer's home directory. This will break on any other machine (VPS, CI, other developers). The agent's `run_command` tool uses this as `cwd`, meaning all git operations will fail or target the wrong repo on any non-yapilwsl environment.

**Mitigation**: Replace with dynamic resolution: `WORKSPACE_ROOT = Path(__file__).resolve().parents[1]` or use `os.getcwd()` / project root detection via pyproject.toml location.

#### 5. 🟠 [High] `admin/dotenv.py line 3 — hardcoded API key in plaintext`

**Description**: `api_key = "localfreegemini"` is a hardcoded credential in a Python source file tracked by git. This file is imported by at least 6 scanner modules (find_duplication.py, find_circular_deps.py, find_async_hazards.py, find_type_safety.py, find_dead_code.py, update_files_metadata.py). While this appears to be a local mesh proxy key, hardcoding any credential in source is a security hygiene violation and sets a dangerous precedent.

**Mitigation**: Replace with `api_key = os.getenv("ADMIN_LLM_API_KEY", "")` and document the required env var. If this is intentionally a non-secret local key, add a comment explicitly stating it is not a production secret and gate it behind an env var anyway for consistency.

#### 6. 🟡 [Medium] `src2/interfaces/telegram/db.py lines 1095-1124 — commented-out debug print() statements`

**Description**: The `if __name__ == "__main__"` block at the bottom of db.py contains 6 commented-out `print()` debug statements (lines 1101, 1107, 1117, 1121, 1124). While commented, their presence indicates ad-hoc debugging that was never cleaned up. If uncommented during future debugging, they would leak user data to stdout.

**Mitigation**: Remove the entire `if __name__ == "__main__"` debug block (lines 1095-1126) or move it to a dedicated test/debug script in `scratch/`.

#### 7. 🟡 [Medium] `src2/engine/openrouter.py line 192 — print() to stdout in production path`

**Description**: `print(f"\n❌ Google API Error Response: {response.text}\n")` writes raw API error responses to stdout. This bypasses the logging framework entirely — no structured JSON, no log level, no timestamp. In production, this output is lost or intermixed with stdout noise. The response text may contain sensitive data.

#### 8. 🟡 [Medium] `src2/engine/bazi_data.py lines 874, 890 and bazi_math.py lines 220-221 — TODO markers in production engine`

**Description**: Four TODO comments remain in the deterministic engine: `# TODO: core_elements vary by stem combination — populate per instance` (bazi_data.py:874, 890) and `# TODO: Tune Extreme_Strong DSI bonus` / `# TODO: Tune Extreme_Weak DSI bonus` (bazi_math.py:220-221). **Mitigation**: Either complete the TODO items or document them explicitly in `_docs/MANUAL/infrastructure/11_FALLBACK_CODES.md` as known limitations with their impact on forecast accuracy.

#### 9. 🟢 [Low] `src2/interfaces/telegram/db.py — `save_daily_forecast` parameter name `narrative_cache` misleading`

**Description**: The parameter is named `narrative_cache` (line 821) but the semantic intent is `narrative` (the LLM-generated narrative text). The old column was `narrative_cache` but the migration renamed it to `narrative`. The parameter name perpetuates the obsolete "cache" mental model that KI 05 explicitly rejects.

**Mitigation**: Rename parameter from `narrative_cache` to `narrative` in the function signature and all internal references (this is a subset of the Critical fix above).

#### 10. 🟢 [Low] `src2/interfaces/telegram/chronomancer/forecast_store.py line 10 — `Database()` module-level instantiation`

**Description**: `db = Database()` at module level in forecast_store.py creates a database connection at import time. If the import happens before environment variables are loaded (e.g., during test collection), it may connect with wrong credentials or to SQLite instead of PostgreSQL. Same pattern exists in coordinator.py (line 30).

**Mitigation**: Use lazy initialization: a `_db = None` module variable with a `def get_db()` factory that creates the Database on first call, or pass db as a dependency rather than module-level singleton.

#### 11. ℹ️ [Informational] `src2/core/schemas/__init__.py — empty, no DailyForecastRecord export`

**Mitigation**: Add `from .daily_forecast import DailyForecastRecord` to `__init__.py` and update forecast_store.py to import from `src2.core.schemas` instead of the deep path.

#### 12. ℹ️ [Informational] `src2/interfaces/telegram/chronomancer/coordinator.py lines 213, 312, 326, 385, 498 — lazy imports inside async functions`

**Description**: `forecast_store` imports are done inside function bodies (5 locations) rather than at module top. This is intentional to break circular imports (documented in KI 04). **Mitigation**: No action required — this is a documented architectural pattern. Consider adding a comment referencing the circular dependency rationale at each lazy import site.
